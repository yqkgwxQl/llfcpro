## question3：既然一条消息装不下那么多 apply，为什么不多发几条消息？

**问题原文**：我为什么在用户登录时要直反给他 10 条 apply？既然一条消息包含不了那么多 apply，为什么我们不多发几条呢？

### 一句话结论

> "多发几条消息"技术上完全可行（微信的离线消息就是分页/分条拉的），但它把一个**一次成型的批量数据**拆成了 N 个**可能各自失败**的独立事务；而真正的浪费其实在 `toStyledString()` 的序列化体积上 —— 先换成 compact 更划算。

### 一、现在为什么只给 10 条

三个约束叠在一起：

```text
MAX_LENGTH = 2048 字节（const.h:58，超了接收端直接 Close）
      ×
toStyledString() 序列化（带缩进换行，一条申请 ~150-200 字节）
      ×
登录响应里还要塞 uid/name/nick/email/icon/desc/sex/error...
```

算下来 **10 条 ≈ 1.6-1.8 KB**，已经贴着 2048 的天花板。

### 二、改成分条发的 5 个代价

#### ① 历史数据和实时推送会混淆

项目里已经有专门干"实时通知"的消息类型：

```cpp
ID_NOTIFY_ADD_FRIEND_REQ = 1011,   // 别人此刻申请加我
```

如果登录时也用多条消息推历史申请，客户端收到 1011 时分不清：

- 我刚登录，服务器在补发历史数据？
- 还是我现在在线，有人刚申请加我？

两者 UI 处理完全不同（历史要排序去重，实时要弹提示 + 置顶）。需要再加一种消息类型 + 客户端状态标记。

#### ② 需要额外发明一个"结束标志"

分 3 条还是 30 条？客户端怎么知道"发完了"？

- 要么再加一条 `ID_APPLY_LIST_END`
- 要么在第一条里带个总数

这就变成了一个迷你协议：**开始 → 条目 × N → 结束**。而分页方案里，一个 `has_more: true/false` 就天然解决了。

#### ③ 最要命的一条：丢消息你感知不到

```cpp
// CSession.cc:215
void CSession::Send(short msg_id, std::string msg_data){
    if(_send_que.size() > MAX_SENDQUE){          // MAX_SENDQUE = 1000
        LOGE << "ChatServer send_queue is full, can not add data" << std::endl;
        return;                                   // ← 静默丢弃
    }
```

**分 100 条发 = 100 次独立的丢包机会，而且丢了客户端完全不知道**（没有确认/重传机制）。
单包批量 = 只有 1 次机会，要么整包到，要么整包不到。

#### ④ "一次请求一次响应"的模型被破坏

`ID_CHAT_LOGIN_RSP` 是标准的请求-响应。多发 N 条就变成"一请求多响应"，客户端的登录成功判定时机会变模糊：**第一条到了算登录成功？还是等结束标志？中间断了怎么办？**

#### ⑤ 每条 Send 都有开销

`unique_lock(_send_lock)` + 队列 push + 判断是否触发 `async_write`。100 条 = 100 次。不致命，但比"序列化一个数组一次性发"浪费。

### 三、更关键：瓶颈不是"包数"，是"包体预算"

在讨论拆包之前，**先做这一步，10 行代码，limit 立刻翻倍**：

```cpp
// 现在：带缩进换行，体积最大
return_value.toStyledString()

// 改成 compact（无缩进）
Json::StreamWriterBuilder wb;
wb["indentation"] = "";
std::string out = Json::writeString(wb, rsp);

// 或者老式写法
std::string out = Json::FastWriter().write(rsp);
```

| 序列化方式 | 一条申请 | 2048 字节能放 |
| --- | --- | --- |
| `toStyledString()`（现状） | ~150-200 B | 约 **10-12 条** |
| compact | ~110 B | 约 **15-18 条** |

**体积直接砍掉 40%。** 现在限制 10 条，有一半是序列化方式白白浪费掉的。

### 四、三种方案对比

| 方案 | 协议改动 | 客户端改动 | 丢消息可见性 | 带宽 |
| --- | --- | --- | --- | --- |
| A. 单包 compact + limit 15~18 | 0 | 0 | 1 次机会 ✅ | 最优 |
| B. 分页拉取（已加 1040 / 1041） | 已完成 | 中（游标 + UI） | 每页独立、可重试 ✅ | 按需，最优 |
| C. 分条推送历史 | 新消息类型 + 结束标志 | 中（状态机） | N 次机会、丢了不知道 ❌ | 差（用户可能不看） |

### 五、建议：走 B（拉模式），不要走 C

```text
【登录】ID_CHAT_LOGIN_RSP
        └─ 只带最新 10 条 + "has_more": true

【用户滚动到底】ID_GET_APPLY_LIST_REQ  { begin: 最小id, limit: 10 }
                [服务端] ID_GET_APPLY_LIST_RSP { apply_list, has_more }

【实时】ID_NOTIFY_ADD_FRIEND_REQ (1011) —— 只管"刚刚发生"的，职责清晰
```

四条理由：

1. **按需** —— 绝大多数用户待处理申请就 1~3 条，一次发 100 条纯属浪费带宽和客户端渲染时间；
2. **可重试** —— 某页失败了客户端重发就行，不会出现"少了几条不知道"；
3. **服务端无状态** —— 不用记"给这个用户发到第几条了"；
4. **和实时推送不打架** —— 历史走请求-响应，实时走 1011，天然分离。

### 六、顺带

`ID_GET_APPLY_LIST_REQ = 1040` / `ID_GET_APPLY_LIST_RSP = 1041` 这个号段挺好 —— 跳过了 1015 之后的空间，以后加新协议不容易撞号。
