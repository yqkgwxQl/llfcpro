================================================================================
0. 一页速览
================================================================================

这套日志系统做四件事：

  (1) 提供一个"全局总出口"，把所有日志汇到一处
        —— 对应客户端的 qInstallMessageHandler
        —— 服务端的做法：把 std::cout / std::cerr 的 streambuf 换掉（零改动接管老代码）
  (2) 每条日志带上下文：时间(毫秒) / 级别 / 出处 / 线程号
  (3) 落盘：logs/<服务名>_<yyyyMMdd>[_n].log，按天 + 按大小轮转，每行 flush
  (4) 线程安全：多线程并发写不会互相穿插、不会崩

三个使用入口（任选）：

    LOG_INFO("uid=%d", uid);              // printf 风格：带 file:line、编译期查格式串
    LOGI << "uid=" << uid;                // 流式风格：整行原子（老代码把 cout 换掉即可）
    std::cout << "uid=" << uid << '\n';   // 什么都不改，靠 rdbuf 接管

一句话记住数据流：

    调用点 → 门面(宏 / LogStream / LogStreamBuf) → Logger::handleFrom(加锁)
           → writeLineLocked(拼行) → 文件 + 控制台

1. 文件与职责
================================================================================

Logger.h
  ├─ LogLevel 枚举（Debug / Info / Warn / Error / Fatal）
  ├─ namespace lfclog 的函数声明（active / setActive / enabled / setMinLevel /
  │     minLevel / levelTag / parseLevel / logf）
  ├─ class LogStreamBuf : public std::streambuf   —— 接管 std::cout / std::cerr
  ├─ class Logger : public Singleton<Logger>      —— 门面 + 状态 + 落地
  ├─ class LogStream                              —— 流式写法的临时对象
  └─ 使用宏：LOG_DEBUG/INFO/WARN/ERROR/FATAL 与 LOGD/LOGI/LOGW/LOGE/LOGF

Logger.cc
  ├─ namespace lfclog 的实现（两个全局原子开关 + 级别工具 + logf）
  ├─ 匿名 namespace 的小工具（LocalTime / ShortName / TodayKey / CurrentThreadId）
  ├─ Logger 的实现（GetInstance 永生、Init、install / shutdown、handle*、落盘、轮转）
  ├─ LogStreamBuf 的实现（tlsBuf / overflow / xsputn / sync / emit / flushPending）
  └─ LogStream::~LogStream

注意：LogStreamBuf 与 Logger 是"子对象"关系 —— coutBuf_ / cerrBuf_ 是 Logger 的
      成员（Logger.h:254-255），不是 new 出来的。所以 Logger 永生 ⇒ 这两个缓冲也
      永生 ⇒ std::cout 手里的指针永远不会悬垂。

3. 数据与状态：谁存了什么
================================================================================

3.1 lfclog 命名空间的全局开关（Logger.cc:21-25，匿名 namespace 内）

    std::atomic<bool> g_active{false};                 // 已安装且未 shutdown
    std::atomic<int>  g_minLevel{(int)LogLevel::Info}; // 当前最小输出级别

    为什么放在命名空间作用域、用原子类型？
      · 平凡析构 → 没有"析构"这一步 → 程序任何时刻读它都合法
      · 不依赖 Logger 对象的存活 → 即使单例已被静态析构，读开关也不会 use-after-free
      · 热路径零开销：x86 上 relaxed load 就是一条普通 mov（实测过）

3.2 Logger 的状态（Logger.h:242-257）—— 全部由 mutex_ 保护

    mutable std::mutex mutex_;   // 保护下面所有可变状态
    std::ofstream      file_;    // 当前打开的日志文件
    std::string  serviceName_;   // "gateserver" / "chatserver1" ...
    std::string  logDir_;        // "logs"
    std::string  dayKey_;        // 当前文件对应的日期 yyyyMMdd
    std::string  curFile_;       // 当前文件全路径（给 currentFile()）
    std::size_t  size_;          // 当前文件已写字节数（自己记账，不查文件系统）
    std::size_t  maxBytes_;      // 单文件上限
    bool         console_;       // 是否同时打控制台
    bool         installed_;     // 是否已安装（shutdown 后为 false，用于丢弃日志）

    LogStreamBuf coutBuf_{LogLevel::Info,  "std::cout"};   // 接管 cout
    LogStreamBuf cerrBuf_{LogLevel::Error, "std::cerr"};   // 接管 cerr
    std::streambuf* oldCout_ = nullptr;   // 原来的 cout 缓冲（用于还原）
    std::streambuf* oldCerr_ = nullptr;   // 原来的 cerr 缓冲（用于还原）

3.3 LogStreamBuf 的状态（Logger.h:166-181）

    进程内共享的（每个 Logger 一份，两个实例）：
        LogLevel        level_;    // cout 缓冲→Info，cerr 缓冲→Error
        std::string     srcTag_;   // "std::cout" / "std::cerr"（写进日志的"出处"）
        std::streambuf* original_; // 原来是哪个缓冲（!active 时把字符转发给它）
        Logger*         owner_;    // 指回 Logger（裸指针，避免退出期走 GetInstance）

    每个线程各一份的：
        tlsBuf() → std::unordered_map<const LogStreamBuf*, std::string>&
                   键   = 哪个缓冲（&coutBuf_ / &cerrBuf_）
                   值   = 该缓冲在本线程攒着、还没凑成一行的字符

    也就是说：内存里每个线程有一张最多 2 个条目的小表；cout / cerr 两条流各有自己
    的待写字符串，互不干扰。

3.4 为什么"行缓冲"必须每线程一份

    std::cout << "uid=" << uid << " login" << std::endl;   // 4 次 <<，4 次进 streambuf

    若所有线程共享一个字符串缓冲，两线程的字节会交错：
        "uid=uid=1001 1002 loginlogin"   ← 行被撕裂
    每线程一份 ⇒ 一行内不管有多少次 <<，都只有本线程看得见自己的缓冲 ⇒ 整行原子。

4. 生命周期时间轴
================================================================================

  [进程启动]
      │  （std::cout / std::cerr 还是标准库原来的样子；g_active = false）
      ▼
  Logger::Init("chatserver1", level, console, dir, maxFileMB, redirect)
      │
      ├─ GetInstance()  → 首次调用：Singleton<Logger>::GetInstance() 里 new Logger()
      │                    → Logger 构造函数 → install()
      │                       ├─ setOwner(this) 给两个缓冲
      │                       ├─ std::cout.rdbuf(&coutBuf_) / cerr 同理
      │                       │    oldCout_ = 换下来的旧缓冲；同时 setOriginal(oldCout_)
      │                       ├─ std::cerr.unsetf(ios::unitbuf)  ← 否则 cerr 一行会被拆多条
      │                       └─ setActive(true)
      │
      ├─ flushPendingBuffers()           ← 先把残缺行冲出去（此时不持锁）
      ├─ { lock; 写 serviceName_/logDir_/console_/maxBytes_; installLocked(...) }
      ├─ setMinLevel(level)
      ├─ Windows: SetConsoleOutputCP(CP_UTF8)   ← 中文日志不乱码
      └─ LOG_INFO("logger started: ...") + LOG_INFO("log file: %s")   ← 顺手验证通路
      │
      ▼
  [运行期]  三条路径写日志（见第 5 节）；文件按天 / 按大小轮转（见第 7 节）
      │
      ▼
  Logger::GetInstance()->shutdown()          ← 推荐在 main 末尾显式调用
      │
      ├─ flushPendingBuffers()               ← ① 先冲残留（不持锁）
      ├─ setActive(false)                    ← ② 关总闸
      ├─ { lock;
      │     restoreStdStreamsLocked()        ← ③ rdbuf(oldCout_)、还原 cerr 的 unitbuf
      │     file_.flush(); file_.close();
      │     dayKey_.clear(); size_ = 0; installed_ = false; }
      ▼
  [退出]  此后：
      · 宏 → enabled() 先返回 false → 静默丢弃（不碰 Logger 对象）
      · 写 std::cout → 已还原，直接走标准库（不经过我们）
      · ~Logger() 不会执行（Logger 永生，见第 9 节）

5. 三条写日志路径
================================================================================

5.1 路径 A：printf 宏（推荐给新代码）

  LOG_INFO("user %d login from %s", uid, ip.c_str());

  lfclog::logf(LogLevel::Info, "CSession.cc", 88, "user %d login from %s", uid, ip)
   │  [Logger.cc:90]
   ├─ if (!enabled(level)) return;            ← 级别不够，连格式化都不做（零成本）
   ├─ va_start(ap, fmt)                       ← 变长参数游标
   ├─ auto logger = Logger::GetInstance();    ← 永生单例；判空防御
   ├─ logger->handleV(level, file, line, fmt, ap)
   │   │  [Logger.cc:486]
   │   ├─ if (!enabled(level)) return;
   │   ├─ std::vsnprintf(buf, 2048, fmt, ap)  ← 真正解析格式串（唯一一次消费 va_list）
   │   ├─ 长度截断保护：min(n, 2047)
   │   └─ handle(level, file, line, std::string(buf, len))
   │       │  [Logger.cc:464]
   │       ├─ if (!enabled(level)) return;
   │       ├─ src = ShortName(file) + ":" + line      → "CSession.cc:88"
   │       └─ handleFrom(level, src, msg)
   │           │  [Logger.cc:477]
   │           ├─ if (!enabled(level)) return;
   │           ├─ lock(mutex_)  ★ 全系统唯一的写入锁
   │           ├─ if (!installed_) return;            ← 已 shutdown 就丢弃
   │           └─ writeLineLocked(level, src, msg)    → 见第 6 节
   └─ va_end(ap)

  特点：有精确 file:line；格式串由编译器按 printf 规则检查（LOG_PRINTF_ATTR(4,5)）；
        代价是类型不安全，只能靠编译告警兜底。

5.2 路径 B：流式宏（推荐给"迁移老代码"）

  LOGI << "user " << uid << " login from " << ip;

  ::LogStream(LogLevel::Info, "CSession.cc", 88)     ← 临时对象
   │  每一次 << 只是把内容写进 LogStream 内部的 ostringstream oss_
   │  （oss_ 是私有的，别的线程碰不到 → 整行天然原子）
   ▼
  语句结束时 → ~LogStream()                          [Logger.cc:628]
   ├─ if (moved_) return;                            ← 被移动构造搬走过就跳过
   ├─ if (!enabled(level_)) return;
   ├─ 裁掉尾部 '\r'/'\n'（老代码的 << std::endl 不会多出空行）
   └─ Logger::GetInstance()->handle(...)  → 与路径 A 汇合（同一个 handleFrom）

  特点：整行原子（哪怕一行由 10 次 << 组成）；把 std::cout 换成 LOGI 就能顺带指定
        级别，迁移成本最低。

5.3 路径 C：接管 std::cout / std::cerr（老代码零改动）

  std::cout << "abc" << 'd' << std::endl;

  ostream::operator<<  →  rdbuf()（此时等于 &coutBuf_）
   ├─ "abc"     → LogStreamBuf::xsputn("abc", 3)   [Logger.cc:573]
   ├─ 'd'       → LogStreamBuf::overflow('d')      [Logger.cc:556]
   └─ std::endl → put('\n') → overflow('\n') → emit(buf)

  三个入口的分工：
   ┌──────────────────┬────────────────────────┬─────────────────────────┐
   │ 何时触发          │ 函数                    │ 做什么                   │
   ├──────────────────┼────────────────────────┼─────────────────────────┤
   │ 单个字符/put区满  │ overflow(int)          │ '\n'→emit；否则追加      │
   │ 整串输出 << "abc" │ xsputn(const char*, n) │ 扫 n 个字符，遇'\n'就emit │
   │ std::flush        │ sync()                 │ 不管有没有换行，直接 emit │
   └──────────────────┴────────────────────────┴─────────────────────────┘
   （注：std::endl 实际是 put('\n') + flush，所以触发 emit 的是 overflow('\n')）

  emit() 之后：
   │  [Logger.cc:602]
   ├─ if (text.empty()) return;
   ├─ 裁掉尾部 '\r'/'\n'
   ├─ msg.swap(text)                             ← 顺手把缓冲清空复用
   └─ owner_->handleFrom(level_, srcTag_, msg)   → 与路径 A 汇合

  三个"不活跃"的例外 —— !lfclog::active() 时（还没装 / 已 shutdown）：
     overflow / xsputn / sync 都改为 original_->sputc / sputn / pubsync
     → 把字符原样交回标准库原来的缓冲，控制台照常输出。

6. 一行的成型过程
================================================================================

  三条路径最终都进 writeLineLocked(level, src, msg)   [Logger.cc:413，持有 mutex_]

  ① openFileForToday()          ← 需要时选文件 / 切文件（见第 7 节）
  ② 取时间：system_clock::now() 拆成两部分
        秒   → time_t → LocalTime() → std::tm （tm_year+1900、tm_mon+1）
        毫秒 → duration_cast<milliseconds>(...) % 1000
  ③ 拼行（与客户端 logger 的行格式一致）：
        "<yyyy-MM-dd hh:mm:ss.zzz> [<级别>] <出处> thread=<十六进制> [msg:<内容>]\n"

        例：2026-10-25 23:59:53.843 [Info] CSession.cc:88 thread=50a4 [msg:user 10001 login]
              └── 时间 ──┘ └级别┘ └─ 出处 ──┘ └线程┘ └───── 内容 ─────┘

        出处 src 的三种可能：
          宏调用        → "CSession.cc:88"           （文件名 + 行号）
          被接管的流    → "std::cout" / "std::cerr"  （拿不到行号，用流的名字代替）
  ④ 落文件：file_.write(...) → size_ += line.size() → file_.flush()
        · 每行 flush：崩溃也不丢（对齐客户端 stream_.flush() 的做法）
        · size_ 自己记账，下次判断"是否写满"不用问文件系统
  ⑤ 打控制台：Warn 及以上 → stderr，其余 → stdout；随后 fflush
        console_ = false 时跳过这一步

7. 文件选择与轮转决策树
================================================================================

  openFileForToday()      [Logger.cc:378，被 writeLineLocked 每条日志前调用]

  ┌─ file_.is_open() && day == dayKey_ && size_ < maxBytes_ ?
  │        └─ 是 → 直接 return（绝大多数调用走这条路，一次比较就返回）
  └─ 否 → 说明要"选新文件"，继续：
        ├─ 关闭旧文件、size_ = 0、dayKey_ = day
        ├─ create_directories(logDir_)         ← 目录不在就建（失败也不抛）
        └─ for idx = 0 .. 9999:
              名字 = <logDir>/<service>_<yyyyMMdd>[_idx].log
                     idx == 0 → chatserver1_20261011.log       （当天主文件）
                     idx  > 0 → chatserver1_20261011_1.log     （第 1 个轮转文件）
              一次系统调用拿"存在吗 + 多大"：
                    std::error_code e2;
                    sz = filesystem::file_size(名字, e2);
                    exists = !e2;
              选择条件（注意 || 的短路）：
                    if (!exists || sz < maxBytes_)
                        → open(名字, out|app|binary)
                        → size_ = exists ? sz : 0     ← 接上已有大小（重启续写）
                        → curFile_ = 名字
                        → return
                    否则试下一个 idx

  三种触发"选新文件"的情形：
    · 第一次写日志（file_ 还没打开）
    · 跨天（day != dayKey_）
    · 当前文件写满（size_ >= maxBytes_）

  安全设计：
    · app 模式 → 重启不覆盖历史；binary 模式 → 不把 '\n' 变成 "\r\n"
    · idx 上限 10000 是防御（一天不可能有一万个 64MB 文件）
    · 文件打不开（权限/磁盘满）→ file_ 保持关闭 → writeLineLocked 里
      "if (file_.is_open())" 不成立 → 文件输出静默丢弃，但控制台照常打印、程序不崩
    · 单文件可能略超上限一行（判断在"写下一行之前"做）


================================================================================
8. 并发模型：锁的分工
================================================================================

  全系统只有一把锁：Logger::mutex_。它保护"拼行 / 落盘 / 文件状态"这一段。

  ┌────────────────────────────────────────────┬──────────────┬──────────────────┐
  │ 函数                                        │ 锁的约定      │ 备注              │
  ├────────────────────────────────────────────┼──────────────┼──────────────────┤
  │ lfclog::active / enabled / setMinLevel      │ 不加锁        │ 原子变量          │
  │ lfclog::minLevel / levelTag / parseLevel    │ 不加锁        │ 纯函数            │
  │ lfclog::logf                                │ 不加锁        │ 先判级别          │
  │ ~LogStream                                  │ 不加锁        │ 调 handle 才加锁  │
  │ LogStreamBuf::overflow / xsputn / sync      │ 不加锁        │ 只碰本线程数据    │
  │ LogStreamBuf::emit / flushPending           │ 不加锁        │ 交给 handleFrom   │
  │ Logger::handle / handleFrom / handleV       │ 自己加锁      │ handleFrom 加锁   │
  │ Logger::writeLineLocked                     │ 必须已持锁    │ 后缀 Locked       │
  │ Logger::openFileForToday                    │ 必须已持锁    │ 只被 Locked 调用  │
  │ Logger::installLocked / restoreStdStreams...│ 必须已持锁    │ 后缀 Locked       │
  │ Logger::flushPendingBuffers                 │ 禁止持锁 ★    │ 持锁会自锁死      │
  │ Logger::Init / shutdown / currentFile       │ 内部安排      │ 见第 4 节         │
  └────────────────────────────────────────────┴──────────────┴──────────────────┘

  命名约定（看到名字就该知道能不能调）：
    · 带 Locked 后缀 → 调用者必须已持锁
    · 不带后缀       → 自己负责加锁，或完全不涉及共享状态

  为什么 flushPendingBuffers() 禁止持锁（自锁死流程）：
    ① 线程 T 拿到 mutex_
    ② T 调 flushPendingBuffers()
    ③ → LogStreamBuf::flushPending() → emit(buf)
    ④ → owner_->handleFrom(...)
    ⑤ → handleFrom 里再次 std::lock_guard<std::mutex>(mutex_)
    ⑥ 同一线程二次锁非递归 mutex → 未定义行为 → Windows 上实际就是永久卡死
    （没有任何线程能解开，因为唯一持有者就是自己）
    所以 Init / shutdown 都是"先 flush（无锁）、再加锁"。

  锁之外的两个同步手段：
    · g_active / g_minLevel 用 std::atomic（每行日志都要读，不能加锁）
    · TLS 行缓冲把"攒行"阶段变成线程私有数据（完全不需要锁）

9. 为什么 Logger 要"永生"
================================================================================

  代码：Logger::GetInstance()   [Logger.cc:172]

      std::shared_ptr<Logger> inst = Singleton<Logger>::GetInstance();
      static std::shared_ptr<Logger>* forever = new std::shared_ptr<Logger>(inst);
      return inst;

  效果：堆上那个 shared_ptr 对象永不 delete → 引用计数永不归零 → ~Logger() 不执行。

  原因一：递归析构（曾真实崩溃）
    ~Logger() → shutdown() → 冲残留 → emit() → （早期版本）Logger::GetInstance()
    此时 shared_ptr 计数已是 0，这次拷贝把控制块"复活"，临时对象析构又回到 0
    → 再次 _M_dispose() → 又一次 ~Logger() → 对象被 delete 两次 → 堆损坏
    （实测退出码 0xC0000374 / 0xC0000409；插桩能看到两遍 "~Logger / shutdown ENTER"）
    修复：① LogStreamBuf 改用裸指针 owner_，不走 GetInstance()；
          ② 加上"永生"，从根上保证 ~Logger() 不在退出期执行。

  原因二：静态析构顺序不可依赖
    本项目其它管理器（RedisMgr / LogicSystem / MysqlMgr ...）都放在
    Singleton<T>::_instance 这个"类静态成员"里，它和 Singleton<Logger>::_instance
    谁先析构，标准不作保证。若 Logger 先死，别人析构函数里的 LOG_xxx 就是
    use-after-free。Logger 永生后，这类问题在日志库这一侧直接消失。

  static 的作用（别漏）：
    GetInstance() 每条日志都会调用。没有 static 就每次 new 一个 shared_ptr 且永不
    释放 → 每行日志泄漏一个对象。static 保证"只 new 一次"（且初始化线程安全）。

  代价：一个 Logger 对象 + 一个 shared_ptr 对象 + 控制块，几百字节，一次性；
        另有每线程一份 tlsBuf（最多 2 个条目），线程池固定所以有界。
        进程退出时由操作系统统一回收。

  注意：(void)forever; 只是压掉 -Wall 的 unused-variable 警告，对引用计数没有任何影响。

10. 关键约束清单（10 条不能做错的事）
================================================================================

  1) Logger::Init 必须是 main 的第一件事，且早于 ConfigMgr::GetInstance()
     —— 否则 ConfigMgr 构造时那句 "Config path: xxx" 抓不到。

  2) 4 个服务的 serviceName 必须不同（gateserver / statusserver /
     chatserver1 / chatserver2）—— 否则多个进程写同一个文件。

  3) 不要持 mutex_ 调用 flushPendingBuffers / emit / handleFrom / handle
     —— 见第 8 节的自锁死流程。

  4) oldCout_ / oldCerr_ / original_ 指向的是标准库的对象：
     只能借用，绝不能 delete，也不要越过它们的生命周期。

  5) va_list 只能消费一次：handleV 里那个 vsnprintf 是唯一消费者。
     若要格式化两遍，必须先 va_copy。

  6) 级别枚举不能叫 ERROR / TRACE：windows.h 里有 #define ERROR 0，
     而 Boost.Asio 会间接包含它 → LogLevel::ERROR 预处理后变成 LogLevel::0。

  7) windows.h 的 min/max 宏会污染 std::min/std::max，
     代码里写成 (std::min)(...) 加括号规避。

  8) 别把密码写进日志：MysqlDao.cc 里有 std::cout << "Password: " << pwd，
     RedisMgr.cc 也会打印 key/value —— 迁移时删掉或降到 Debug。

  9) 每行 flush = 每行一次 write 系统调用。Debug 级别在热路径上会直接压到业务线程，
     生产环境默认 Info（实测约 108 字节/行，1000 行/秒 ≈ 9.3 GB/天）。

 10) shutdown() 之后再写日志是"静默丢弃"，不是崩溃：
     宏走 enabled() 先返回 false；一致性靠这一条兜底。

11. 状态机：active / installed / 级别
================================================================================

  g_active    installed_   行为
  ----------  -----------  -------------------------------------------------------
  false       false        初始状态：宏直接返回；std::cout 还是标准库的
  true        true         install() 之后：三条路径全部工作
  false       false        shutdown() 之后：宏静默丢弃；std::cout 已还原

  另外 g_minLevel 独立生效：只有 enabled(level) 为 true 的调用才会真正落盘。

  所以"一条日志都没有"时，按顺序检查三个开关：
      ① Init() 调了吗（g_active / installed_）
      ② 级别够吗（g_minLevel 是否比你的调用级别高）
      ③ 文件打得开吗（目录权限 / 磁盘；打不开则只有控制台有输出）

13. 附：几个已经澄清过的易错点
================================================================================

  · (void)forever; 和 (void)(*forever); 都不是"置空"，也不会让引用计数 -1。
    它们的语义是"求值后丢弃结果"，对被丢弃的左值不发生拷贝，所以计数根本不变。
    真正会 -1 的只有：reset()、delete forever、或者让一份真的拷贝离开作用域。
    （汇编层面：(void)p; 一条指令都不生成。）

  · reverse_iterator::base() 是"反向 → 正向"的转换，且结果指向该反向迭代器所指
    元素的【右边一格】（rbegin().base() == end()）。它没有"双向等价"的说法，
    正向迭代器身上也没有 base()。

  · 指针没有"析构动作"（平凡析构）。线程结束时只是回收 map 这个指针变量的存储，
    不会去释放它指向的 map —— 那正是本设计刻意保留的泄漏。

  · std::endl 等于 put('\n') + flush，所以触发行输出的通常是 overflow('\n')，
    而不是 sync()；sync() 负责 std::flush 和 shutdown 时的残留冲刷。

  · 日志系统接管的是 C++ 流（std::cout / std::cerr），不接管 C 的 printf / stdout。
    两者在 sync_with_stdio(true) 时共享同一个底层文件，但 printf 的字符不会经过
    我们的 LogStreamBuf。
