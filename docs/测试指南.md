# 测试指南（Testing Guide）

> 适用对象：本仓库（C++ 后端 + Qt 客户端）的日常自检与故障演练。
> 最后更新：2026-11-11

---

## 1. 为什么需要这份文档

项目里有五类东西可能坏，但它们「坏」的表现差别很大：

| 类别 | 典型故障 | 能否自动化 |
|---|---|---|
| 构建产物 | exe 没编出来 / 版本过期 | ✅ 完全可自动化 |
| 配置 | 少 Key、端口非法、两节点端口冲突 | ✅ 完全可自动化 |
| 基础设施 | MySQL / Redis 没起、密码错 | ✅ TCP + ping 可自动化 |
| 服务 | 进程没起、端口没监听 | ✅ 端口 / 进程可自动化 |
| 运行质量 | 连接反复重建、ERROR 刷屏 | ✅ 日志扫描可部分自动化 |
| 客户端 UI | 界面渲染、交互流程 | ❌ 只能手工（截图/操作清单） |

`tools/test/health-check.ps1` 覆盖前五类；第六类见本文第 6 节的手工清单。

## 2. 测试工具

本机默认是 **Windows PowerShell 5.1**（没有 `pwsh`），凡是用到命令的地方都这样写：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools\test\<脚本>.ps1 <参数>
```

> 如果装了 PowerShell 7，把 `powershell` 换成 `pwsh` 即可，参数完全相同。
> `-ExecutionPolicy Bypass` 只是本次运行放行脚本，不修改系统策略。

### 2.1 脚本清单

| 脚本 | 作用 | 会不会改环境 |
|---|---|---|
| `tools/test/health-check.ps1` | **只检查**：L0 结构、L1 配置、L2 依赖、L3 端口/进程、L4 日志 | 否（纯只读） |
| `tools/test/infra-ctl.ps1` | **启停基础设施**：MySQL（Windows 服务）、Redis（redis-server.exe） | 是（启停服务/进程） |
| `tools/test/test-run.ps1` | **跑场景**：调上面两个脚本，按场景准备环境 → 断言 → 恢复现场 | 是（场景需要时） |
| `tools/test/service-run.ps1` | 启动整套服务（可带客户端）并跑在线检查，结束自动清理 | 是（场景需要时） |
| `tools/test/stack-ctl.ps1` | **后台栈控制**：Start/Stop/Status，服务脱离当前作业，命令立即返回 | 是（启停服务/进程） |
| `tools/test/api-test.ps1` | 接口级写库测试：备份 → 注册 → 校验 → 清理 → 对账 | 是（会写库，默认 dry-run） |
| `tools/test/doc-sync.ps1` | 文档同步检查（链接/路径/端口/脚本引用） | 否（纯只读） |

### 2.2 测试矩阵：离线 / 在线 × 启动 / 未启动

> “离线”= 不做任何网络探测（`-NoNetwork`）；“在线”= 探测 TCP / 端口 / HTTP。
> 基础设施指 MySQL 与 Redis。

| # | 场景 | MySQL | Redis | 网络探测 | 预期结果 | 使用命令 |
|---|---|---|---|---|---|---|
| 1 | **离线·基础设施均未启动** | 停 | 停 | 关 | 只看仓库/配置/日志，通常 `exit 0` | `health-check.ps1 -NoNetwork` |
| 2 | **离线·基础设施均已启动** | 起 | 起 | 关 | 与 #1 **结果一致**（离线不探测，启动与否不影响） | `health-check.ps1 -NoNetwork` |
| 3 | **在线·基础设施均未启动** | 停 | 停 | 开 | `exit 1`，L2 出现两条 FAIL（MySQL / Redis 连通性） | `health-check.ps1` |
| 4 | **在线·基础设施均已启动** | 起 | 起 | 开 | `exit 0`（服务未跑时会有 L3 WARN，属正常） | `health-check.ps1` |
| 5 | **在线·Redis 未启动** | 起 | 停 | 开 | `exit 1`，仅“Redis 连通性 FAIL” | `test-run.ps1 -Scenario redis-down`（会自动停/起并恢复） |
| 6 | **在线·MySQL 未启动** | 停 | 起 | 开 | `exit 1`，仅“MySQL 连通性 FAIL” | `test-run.ps1 -Scenario mysql-down`（**需管理员**） |
| 7 | **在线·整套服务 + 客户端** | 起 | 起 | 开 | `exit 0`，health-check 无 FAIL，客户端主窗口出现 | `service-run.ps1 -WithClient` |

补充说明：

- **#1 与 #2 必须一致**——如果离线模式下两者结果不同，说明脚本里混进了网络调用，属于 bug。
- **#3 / #4 的差别只在 L2**；L0/L1/L4 不受基础设施状态影响。
- **#5 / #6 是“单点故障”场景**，用来验证报错定位是否准确（只报坏的那一个，不连累另一个）。

### 2.3 基础设施控制（infra-ctl.ps1）

```powershell
# 查看状态（服务名、端口监听、Redis 是否由脚本启动）
powershell ... -File tools\test\infra-ctl.ps1

# 启动全部（MySQL 走服务，Redis 走 redis-server.exe）
powershell ... -File tools\test\infra-ctl.ps1 -Action Start -Target All

# 只启动/停止 Redis
powershell ... -File tools\test\infra-ctl.ps1 -Action Start -Target Redis
powershell ... -File tools\test\infra-ctl.ps1 -Action Stop  -Target Redis

# 停止“不是脚本启动的”Redis（默认拒绝，防误杀）
powershell ... -File tools\test\infra-ctl.ps1 -Action Stop -Target Redis -Force
```

行为约定：

| 项 | 说明 |
|---|---|
| MySQL | 自动发现名字含 `mysql` 的 Windows 服务（本机为 `mysql80`）；**启停服务需要管理员权限**，非管理员会明确提示而不是静默失败 |
| Redis | 读取节点 `config.ini` 的 `[Redis] Port/Passwd`，生成临时配置启动；`save ""` **不落盘**，数据目录放在 `%TEMP%` |
| 归属识别 | 脚本把启动的 Redis PID 记到 `%TEMP%\llfc-infra-redis.pid`，之后只停止“自己启动的”实例 |
| 密码 | 只写入临时配置文件（`%TEMP%`），不打印、不出现在命令行参数里 |
| 清理 | 停止 Redis 时删除临时配置与 PID 文件 |

### 2.4 场景运行器（test-run.ps1）

```powershell
# 离线场景
powershell ... -File tools\test\test-run.ps1 -Scenario offline

# 在线场景（基础设施已就绪；-StartInfra 会先尝试拉起 MySQL/Redis）
powershell ... -File tools\test\test-run.ps1 -Scenario ready -StartInfra

# Redis 单点故障：停 → 期望 FAIL → 恢复 → 期望 PASS → 恢复现场
powershell ... -File tools\test\test-run.ps1 -Scenario redis-down

# MySQL 单点故障（需要管理员权限，否则自动跳过）
powershell ... -File tools\test\test-run.ps1 -Scenario mysql-down
```

场景结束时都会**尽量恢复原状**：

- Redis 若是脚本启动的 → 测试结束自动停止（恢复成“之前没在跑”的状态）；
- MySQL 若是脚本停止的 → 测试结束自动重新启动；
- 若一开始 Redis 就在运行（不是脚本启动的），`redis-down` 会因“拒绝停止他人的实例”而失败——这是有意的保护，加 `-Force` 才能强停。

> 注意：`ready -StartInfra` 会**留下**运行中的基础设施，方便你接着做手工测试。
> 想恢复成“只有 MySQL 在跑、Redis 关闭”的状态：
> `powershell ... -File tools\test\infra-ctl.ps1 -Action Stop -Target Redis`

### 2.5 整套服务与客户端（service-run.ps1）

把“开四个窗口”的流程自动化：按顺序启动 Redis → StatusServer → GateServer → ChatServer(chatserver1)，
等端口就绪后跑一次在线健康检查，结束时清理本脚本启动的进程。

```powershell
# 只起服务并检查
powershell ... -File tools\test\service-run.ps1

# 同时启动 Qt 客户端，并确认主窗口出现
powershell ... -File tools\test\service-run.ps1 -WithClient

# 保留现场（不清理，方便继续手工点界面）
powershell ... -File tools\test\service-run.ps1 -WithClient -KeepRunning
```

| 行为 | 说明 |
|---|---|
| 启动顺序 | Redis → StatusServer(50052) → GateServer(8080) → ChatServer(8090 / 50055) |
| 端口等待 | 每个端口最多等 `-WaitSeconds`（默认 15s），超时会打印该服务的日志尾部 |
| 健康检查 | 全部就绪后自动跑 `health-check.ps1`，有 FAIL 则退出码为 1 |
| 客户端 | `-WithClient` 时启动 `llfcchat.exe`，最多等 30s 检测主窗口；**只验证能起来+窗口出现**，界面交互仍需按第 6 节手工做 |
| 清理 | 默认停止本次启动的所有进程；Redis 只在“本次由脚本启动”时才停 |
| 日志 | 各进程 stdout/stderr 写到 `%TEMP%\llfc-service-run\` |

> **客户端启动注意**：本机 `llfcchat.exe` 必须让 **MinGW 15.1 的运行时**先于 Qt 的 `bin` 被加载，
> 否则会以 `0xC0000139`（找不到 DLL 入口点）立即退出。脚本已按
> `E:\YingYongRuanjian\mingw64\bin` → `F:\...\Qt\6.11.0\mingw_64\bin` 的顺序拼 PATH；
> 手工启动时也要保证这个顺序。

> **在后台作业 / CI 中使用**：`service-run.ps1` 用 `Start-Process` 启动服务，
> 子进程属于当前作业；带 `-KeepRunning` 时，作业会一直 `running` 直到服务退出。
> 需要“启动后立即返回、服务留在后台”时，改用 §2.5.1 的 `stack-ctl.ps1`。

#### 2.5.1 后台栈控制（stack-ctl.ps1）

```powershell
# 启动 Redis + 三个服务（命令约 30~40 秒后返回，服务继续在后台跑）
powershell ... -File tools\test\stack-ctl.ps1 -Action Start

# 查看端口与状态文件
powershell ... -File tools\test\stack-ctl.ps1 -Action Status

# 按端口停止本次启动的服务；若 Redis 是 Start 时拉起的，会一并停止
powershell ... -File tools\test\stack-ctl.ps1 -Action Stop
```

| 项 | 说明 |
|---|---|
| 与 `service-run.ps1` 的区别 | `stack-ctl` 用 WMI `Win32_Process.Create` 启动，进程**不属于当前作业**，所以命令能立即返回 |
| 状态文件 | `%TEMP%\llfc-stack\state.json`（记录端口与“Redis 是否由本次启动”） |
| 日志 | `%TEMP%\llfc-stack\<服务名>.log` |
| 停止依据 | 按端口找 `OwningProcess`，只影响本仓库配置里的 50052/8080/8090/50055 |
| 适用场景 | 交互式“先起栈、再跑别的脚本”，或 CI 里分步执行 |

> 典型分步流程（避免一条长命令被超时中断）：
> 1. `stack-ctl.ps1 -Action Start`
> 2. `api-test.ps1 -AllowWrite`
> 3. `stack-ctl.ps1 -Action Stop`


### 2.6 参数与退出码

`health-check.ps1`：

| 参数 | 默认 | 说明 |
|---|---|---|
| `-Root` | 脚本所在目录的上两级 | 仓库根目录 |
| `-TimeoutMs` | `1500` | 单个 TCP 探测超时 |
| `-NoNetwork` | 关 | 跳过所有网络检查（L2 / L3） |
| `-Json` | 关 | 输出 JSON 数组 |

退出码：

| 码 | 含义 | 使用场景 |
|---|---|---|
| `0` | 没有 FAIL（可能有 WARN / SKIP） | 可以继续下一步 |
| `1` | 至少一个 FAIL | 在 CI 或脚本里直接中断 |

`test-run.ps1` 的退出码同规则：所有断言通过为 `0`，任一断言失败为 `1`。

### 2.7 接口级写库测试（api-test.ps1）

这是**唯一会写数据库**的测试，默认 dry-run，必须加 `-AllowWrite` 才执行：

```powershell
# 先保留现场（服务别停）
powershell ... -File tools\test\service-run.ps1 -KeepRunning

# 另一个终端：看计划（不写库）
powershell ... -File tools\test\api-test.ps1

# 真正执行
powershell ... -File tools\test\api-test.ps1 -AllowWrite
```

它做什么（严格「先备份、只删自己造的数据、最后对账」）：

| 步骤 | 动作 |
|---|---|
| 1 | 记录基线：`user` 行数、`user` 表 `AUTO_INCREMENT`、`user_id` 发号器当前值 |
| 2 | `mysqldump` 备份 `user` / `user_id` 到 `%TEMP%\llfc-api-backup\<时间戳>\user.sql` |
| 3 | Redis 写入 `code_<测试邮箱>`，POST `/user_register`（唯一邮箱/用户名 `llfctest_<时间戳>`） |
| 4 | 断言：响应 `error==0`、库里能查到该邮箱、`uid>0` |
| 5 | 清理：`DELETE` 测试用户 → 恢复 `user_id` 发号器 → 重置 `AUTO_INCREMENT` → `DEL` 验证码 |
| 6 | 对账：`user` 行数与 `user_id` 必须回到基线；不一致且加了 `-RestoreOnMismatch` 时从备份还原 |

> 为什么不能只 `DELETE`：注册会同时推进 `user_id` 发号器与 `user.AUTO_INCREMENT`，不还原的话下一次注册的 uid 会跳号。
> 测试失败时也会走清理（`finally`），并用唯一前缀保证只删自己插入的行。

## 3. 检查项（L0 ~ L4）

### L0 仓库结构

| 检查 | 失败级别 | 说明 |
|---|---|---|
| `client/llfcchat/build/llfcchat.exe` | WARN | 客户端没编时不影响后端 |
| `server/GateServer/build/GATESERVER.exe` | FAIL | 网关缺失 |
| `server/StatusServer/build/STATUSSERVER.exe` | FAIL | 状态服务缺失 |
| `server/ChatServer/build/CHATSERVER.exe` | FAIL | 聊天服务缺失 |
| `server/sql/schema.sql` | WARN | 结构脚本缺失 |
| `docs/测试指南.md`、`docs/改造记录.md` | WARN | 文档缺失 |
| `tools/test/*.ps1` | WARN | 测试脚本缺失 |

### L1 配置

对 `server/ChatServer/nodes/*/config.ini` 逐个检查：

- `[SelfServer]` 的 `Name / Host / Port / RPCPort` 是否齐全；
- 端口是否为 1~65535 的数字；
- `[Mysql]`、`[Redis]` 的 `Host` 与 `Port` 是否齐全；
- `[PeerServer] Servers` 里列的每个名字，是否都有对应段且 `Host/Port` 合法；
- 多节点时：`Name`、TCP 端口、gRPC 端口是否**互不重复**。

另外若存在 `server/GateServer/config.ini`、`server/StatusServer/config.ini`，会检查它们的监听端口。

> 配置里含密码，脚本只读不打印；`redis-cli` 调用通过环境变量 `REDISCLI_AUTH` 传密码，不出现在命令行上。

### L2 依赖连通性

- MySQL：对 `[Mysql] Host:Port` 做 TCP 连接（默认 1.5s 超时）；
- Redis：同上；若本机装了 `redis-cli`，追加一次 `PING`（用环境变量传密码，并加 `--no-auth-warning`）。

失败通常意味着：服务没起、端口写错、Docker 端口映射没做对。

### L3 服务监听与进程

- 按配置探测各端口是否处于 `LISTEN`：ChatServer TCP/gRPC、GateServer、StatusServer；
- 探测 `GATESERVER / STATUSSERVER / CHATSERVER / llfcchat` 进程是否存在；
- 若 GateServer 在监听，追加一次 `GET http://127.0.0.1:<port>/` 的 HTTP 探活（只取根路径，不触发业务写）。

**未监听 / 未运行只报 WARN**——因为测试时服务可能本来就没起。

### L4 日志健康

对每个节点的 `logs/` 取最新日志文件，读末尾 200 行：

| 指标 | 触发条件 | 级别 | 含义 |
|---|---|---|---|
| `[ERROR]` / `[FATAL]` 条数 | > 3 | FAIL | 运行期错误偏多 |
| `补连接失败` | > 0 | WARN | Redis 抖动 / 池在重建连接 |
| `连接池等待超时` | > 0 | WARN | 借不到连接（池空或 Redis 不可达） |
| `认证成功` | 近 10 分钟 ≥ 10 | WARN | 连接被反复重建（疑似抖动） |
| 日志文件存在性 | 不存在 | WARN | 服务没跑过，或日志目录配错 |

> 正常情况下，`认证成功` 只在启动建池（5 条）和故障补位时出现；如果它持续增长，说明连接在反复断开重建。
> 检查只看**近 10 分钟**内的条数，避免把一天内多次重启的累计值误判成抖动。

## 4. 典型输出与解读

```text
Area    Check                    Status Detail
----    -----                    ------ ------
L0 结构 client/llfcchat/build/... PASS   12,345 KB
...
L2 依赖 MySQL 连通性              PASS   127.0.0.1:3308
L2 依赖 Redis 连通性              FAIL   127.0.0.1:6380 timeout 1500ms
L3 服务 chatserver1 TCP           WARN   8090 未监听（服务未启动？）
...
汇总: PASS=28  WARN=9  FAIL=1  SKIP=0
结论: 存在 FAIL，请按上表逐项修复。
```

| 看到 | 优先排查 |
|---|---|
| `Redis 连通性 FAIL` | Redis 是否启动、端口/密码是否与 `config.ini` 一致 |
| `MySQL 连通性 FAIL` | 同上；注意 Docker 映射端口 |
| `端口合法性 FAIL` | `config.ini` 里 `Port/RPCPort` 写成了非数字或超范围 |
| `节点 TCP/gRPC 端口唯一 FAIL` | 两份节点配置抄成了同一组端口 |
| `对端段 FAIL` | `PeerServer.Servers` 里的名字没有对应段 |
| `连接抖动 WARN` | 结合日志看是否有 `补连接失败`，多半是 Redis 不稳 |

## 5. 故障注入（验证自愈能力）

这些测试**会**影响运行中的服务，只在本地环境做。每一步都说明了「期望现象」，用来验证前面改造的可靠性逻辑。

> 本机没有 Docker：MySQL 是 Windows 服务 `mysql80`，Redis 是 `F:\YingYongRuanJian3\redis\redis-server.exe`。
> 下面的命令都用 `tools/test/infra-ctl.ps1` 统一处理，不需要记具体安装方式。

### 5.1 停 Redis → 观察降级与恢复

```powershell
# 1) 服务运行中，停掉 Redis（脚本会识别端口并停止；若 Redis 不是脚本启动的，需要 -Force）
powershell -NoProfile -ExecutionPolicy Bypass -File tools\test\infra-ctl.ps1 -Action Stop -Target Redis -Force

# 2) 客户端尝试登录 / 刷新 → 应快速失败，而不是卡死
# 3) 观察日志（每 60 秒一轮）
Get-Content -Wait -Tail 30 server\ChatServer\nodes\chatserver1\logs\chatserver1_<日期>.log
#    期望：每 60 秒 1 条 "补连接失败：redisConnect 无响应（本轮停止扩容）"
#          进程不崩、CPU 不高

# 4) 恢复 Redis
powershell -NoProfile -ExecutionPolicy Bypass -File tools\test\infra-ctl.ps1 -Action Start -Target Redis
#    期望：≤1 分钟 内出现 "认证成功"，之后查询恢复正常
#          用 health-check.ps1 复查：连接抖动指标不再增长
```

> 想一步到位验证“停→失败→恢复→通过”，直接用：
> `powershell ... -File tools\test\test-run.ps1 -Scenario redis-down`（自动恢复现场）。

### 5.2 停 MySQL → 观察启动失败与运行期探活

## 7. 已知限制

1. **脚本只覆盖「可观测」层面**：它能告诉你“端口没通”“日志有 ERROR”，但不能证明业务逻辑正确（比如好友申请的状态流转）。
2. **MySQL 只做 TCP 探活**：没有用 `mysqladmin ping`，因为不同安装方式下命令名/路径不一致；需要更严格时可在 CI 里补。
3. **Redis PING 依赖本机 `redis-cli`**：没装就自动跳过（SKIP）。
4. **日志格式耦合**：L4 按 `[ERROR]` / `[FATAL]` 和中文关键字匹配；如果以后改日志格式，要同步改脚本。
5. **GateServer HTTP 探活只请求 `/`**：401/404 也算“服务活着”，不代表业务接口正常。
