# ChatServer 合并与健壮性改造总结

> 日期：2026-11-08（初稿）／ 2026-11-16（补第 9 节「横向移植」）
> 范围：`server/ChatServer`；2026-11-16 起包含 `GateServer` / `StatusServer` 的数据层移植
> 用途：记录「这次改了什么、为什么改、还剩什么」，避免下次接手时只能翻聊天记录。

## 1. 这次到底在解决什么

### 起因

`server/ChatServer1` 与 `server/ChatServer2` 是两份几乎相同的副本：

| 对比项 | 结果 |
|---|---|
| 源文件 | 40 个，其中 36 个字节级相同 |
| 真正差异 | `CMakeLists.txt` 的 target 名、`message.proto` 的一段注释、`MysqlPool.cc` 的 4 行调试注释、`config.ini` |
| 节点身份来源 | 全部来自配置（`[SelfServer] Name/Port/RPCPort`），代码里没有硬编码 |

结论：**删除一份副本、改成「一个 exe + 每个节点一份配置」几乎零信息损失。**

### 目标演进（有意为之，但要写下来）

| 阶段 | 目标 | 是否本次范围 |
|---|---|---|
| A | 消除节点副本：单 exe + `nodes/*/config.ini` | ✅ 是 |
| B | 启动可靠性：配置/端口校验、快速失败、明确退出码 | ✅ 是 |
| C | 数据层正确性：连接池超时、坏连接处理、事务状态恢复 | 🟨 附带（由 B 引出） |
| D | 横向复制到其它服务、抽公共库 | ⬜ 下一步 |

> 教训：A 做完后目标实际上从「结构」切到了「可靠性」，但当时没有明确记录，
> 导致后面越改越像「不知道自己在修什么」。

## 3. 修复路线（一步引出下一步）

| 阶段 | 起点问题 | 动作 | 引出 |

> 它本身不是 Bug 修复，却长出了 `borrowed_` 记账、`EnsureCapacity`、容量超发、

## 12. 抽出 `server/common`：数据层合并为一份（2026-11-22，BL-07）

### 12.1 为什么要做

12 个数据层/常量文件原本在三个服务里各存一份，靠 `doc-sync.ps1` 的 D7 防漂移。实际代价是：
**改一次 `MysqlDao.cc` 要手动复制两份**，最近两周两次因为漏同步被打回（`MysqlDao.cc` / `RedisMgr.cc` 各一次）。
BL-07 的目标就是让「三个服务共用一份源码」。

### 12.2 最终形态

```
server/common/
├── CMakeLists.txt        # add_library(llfc_common STATIC ...)
├── include/              # 扁平暴露：服务里 #include "Logger.h" / "const.h" 一行都不用改
│   ├── Singleton.h  Logger.h  ConfigMgr.h  AsioIOServicePool.h
│   ├── RedisConPool.h  RedisMgr.h
│   ├── MysqlPool.h  MysqlDao.h  MysqlMgr.h
│   └── data.h  const.h
└── src/                  # 对应实现（Logger / ConfigMgr / AsioIOServicePool / Redis 组 / MySQL 组）
```

各服务的 `CMakeLists.txt` 只多两行：

```cmake
add_subdirectory(${CMAKE_CURRENT_SOURCE_DIR}/../common ${CMAKE_BINARY_DIR}/common)
target_link_libraries(${PROJECT_NAME} PRIVATE llfc_common)
```

依赖（Boost / JsonCpp / hiredis / MySQL Connector）由 `llfc_common` 以 `PUBLIC` 透出，
服务端不需要再重复写一遍 include 路径。

### 12.3 迁移顺序（每步都验证过）

| 4 | 把 D7 改写为「公共库唯一来源」检查 | `doc-sync` PASS=25 |

| 文件 | 处理 |
|---|---|
| `ConfigMgr` | 统一成 ChatServer 的超集（带 `SetConfigPath`）；Gate/Status 不调用就退回原来的 `cwd/config.ini` |

### 13.1 之前是什么样

## 14. 环境问题：Windows 沙箱写权限没有向既有子目录传播（2026-11-23）

> 这一节记录**开发机环境**问题，不是代码问题。遇到「`workspace-write` 模式下只有工作区根目录能写、子目录全部 Access denied」时先看这里。

### 14.1 现象

- DSH 以默认的 `workspace-write` 策略运行时，写 `docs/`、`server/` 等**既有子目录**失败（`UnauthorizedAccessException`），写**工作区根目录**却成功；
- 于是每次改文件都要临时提权到 `danger-full-access`，审批弹窗不断；
- 早期还会出现 `windows-acl-run: --temp is not an existing directory`（那是另一个问题，现已不复现）。

### 14.2 根因（在 DSH 的沙箱实现里，不在本仓库）

| 观察 | 结论 |
|---|---|
| 根目录上有 `S-1-4-<hash>` 的写权限项（显式），所有子目录都没有 | 授权只作用在根 |
| 这些子目录都**没有**禁用继承（`AreAccessRulesProtected = False`） | 不是被"保护"挡住的 |
| 在根下**新建**目录 → 能拿到该权限项（标记为继承） | 继承只在**创建时**发生 |
| `types-Cl_DXjhk.js` 的 `mergeAndApply()` 调用 `SetNamedSecurityInfoW(path, 1, 4 或 20, ...)` | **缺少 `0x100`（`SE_DACL_AUTO_INHERIT_REQ`）**，系统不会把可继承权限项补到既有子对象 |
| `grantWrite()` 里有"三项精确命中就 return"的快速路径 | 一旦根上已有该项，**永不重试传播**，问题不可自愈 |
| `workspaceWriteSid()` = `sha256(workspaceRoot)`（已验证：`E:\zhongzhuan2\llfcchatpro` → `S-1-4-664767861-45115372`） | SID 由路径派生、**每个会话相同** |

### 14.3 已尝试的修复与实际结果

**做了什么**（2026-11-23，本机执行，已备份 8194 个对象）：

```powershell
icacls "E:\zhongzhuan2\llfcchatpro" /save "$env:USERPROFILE\dsh-acl-backup-<时间戳>.acl" /T /C
icacls "E:\zhongzhuan2\llfcchatpro" /inheritance:e /T /C
```

**ACL 层结果**：✅ 成功。`docs` / `server` / `server\common` / `client` / `tools` / `server\proto`
现在都带上了 `S-1-4-664767861-45115372`（`继承=True`），`Everyone` 的删除限制也补上了。

**但受限写入仍然失败**（关键结论）：

| 操作 | 在 `workspace-write` 下的结果 |
|---|---|
| 用编辑工具改 `docs/改造记录.md` | ✅ 成功（文件工具走宿主进程，不受沙箱令牌限制） |
| 用命令在 `docs\` 新建文件 / 目录 | ❌ `UnauthorizedAccessException` |
| 用命令读取 / 运行只读脚本（`doc-sync`） | ✅ 正常 |

> 也就是说：**DACL 继承已修好，但受限命令的写入仍被拒** —— 还有第二个因素。

### 14.4 第二因素：Low 完整性标签同样只加在根上（已确认）

代码证据（`dsh-sandbox-windows-acl/lib/types-Cl_DXjhk.js`）：

```js
restrictTokenIntegrity(api, restrictedToken, lowLabelSid);   // 第 1291 行：子进程被降到 Low
// 授权时用 buildLowLabelAcl() 只给“根目录”加 Low 标签（OI|CI），不向既有子对象传播
```

| 事实 | 含义 |
|---|---|
| 沙箱子进程 = Low 完整性（`S-1-16-4096`） | 它只能写"标签为 Low 或更低"的对象 |
| 根目录带 Low 标签（DSH 自检报告 `lowLabel: true`） | 所以根目录可写 |
| 既有子目录**没有**标签（默认 Medium） | Low 进程**不能向上写** → 一律被拒 |

**尝试过的手工修复**：`icacls "<root>" /setintegritylevel (OI)(CI)Low /T /C`
→ 7433 个对象成功、**761 个失败**（这些对象没有改标签的权限，多为 SYSTEM/管理员所有）。
因无法在本会话内验证、且"半成功"有风险，已用 `icacls ... /setintegritylevel (OI)(CI)Medium /T /C` **回滚**（同样 7433 成功 / 761 失败）。

### 14.5 第三方补丁插件对本机场景**无效**（2026-11-23 实测）

社区有一个临时补丁插件 [`masknull/dsh-acl-sandbox-patch`](https://github.com/masknull/dsh-acl-sandbox-patch)，
本机已用 `link:` 方式装到 profile 里：

```json
// home/profiles/web/package.json
"dsh-acl-sandbox-patch": "link:C:/Users/22688/Downloads/dsh-acl-sandbox-patch-0.1.2"
```

**它确实加载了**（启动日志有 `[dsh-acl-sandbox-patch] active — …`），但 `workspace-write` 下写
`docs\`、`server\common\` **依然被拒**。

原因在它的判据（`lib/preload.cjs` 的 `wrapSetTokenInformation`）：

```js
const workspace = workspaceFromArgv()
if (workspace !== null && workspaceHasLowLabel(workspace) === false) return 1  // 跳过降完整性
```

它**只看工作区根目录**是否有 Low 标签。本机的情况是「根有标签、子目录没有」：

| 对象 | Low 标签 | 插件判断 |
|---|---|---|
| 工作区根 | ✅ 有 | 认为"严格环境" → 照常降 Low |
| `docs` / `server` 等子目录 | ❌ 没有 | 被 no-write-up 拒绝 |

所以它覆盖的是"根目录授权直接失败（Win32 5）"那种场景，**覆盖不到本机这一种**。

### 14.6 决策：保持「完全权限」，不修改插件（2026-11-23）

**决定**：日常开发直接使用 `danger-full-access`（会话级切换），**不修改** `dsh-acl-sandbox-patch` 的源码。

理由：

1. **收益低**：完全权限下 `cmake`、`*.ps1`、编译、测试全部正常，改插件只是省掉审批弹窗；
2. **风险高**：本地魔改第三方临时补丁，插件/DSH 一升级就失效，还得在插件目录留说明；
3. **边界代价**：强制降级等于**永久放弃 Low 完整性这一层**；
4. **有更干净的出路**：等上游修复（[#423](https://github.com/deepseek-ai/deepseek-harness/discussions/423) / [#5477](https://github.com/deepseek-ai/deepseek-harness/discussions/5477)）后升级 DSH 并卸载插件。

**重新评估的触发条件**（任一成立再看下面的备选方案）：

- 上游修好 → 升级 DSH + 卸载插件；
- DSH 升级后 `workspace-write` 仍不可用，且出现"长时间无人值守跑命令"的需求；
- 工作区迁到用户目录（`%USERPROFILE%` 下默认带 FullControl，本问题不出现）。

**备选方案（本次未采用，仅记录，防止以后重复调研）**：

1. **给插件加强制降级开关**：让沙箱子进程不再被降到 Low（见下）；
2. **管理员权限把 Low 标签传播到整棵树**：§14.4 已试过非管理员版本（7433 成功 / 761 失败），提权后可能有改善。

方案 1 的改法（`<插件目录>/lib/preload.cjs` 的 `wrapSetTokenInformation()`，在
`informationClass === TOKEN_INTEGRITY_LEVEL` 分支最前面加一行）：

```js
if (process.env.DSH_ACL_PATCH_FORCE_DEGRADED === '1') return 1   // 强制跳过降完整性
```

开启方式：`start_dsh.bat` 里 `set DSH_ACL_PATCH_FORCE_DEGRADED=1`。

| 保留的边界 | 放弃的边界 |
|---|---|
| `WRITE_RESTRICTED` 受限令牌（只能写能力 SID 授权的位置） | **Low 完整性这一层纵深防御** |
| 工作区能力 SID 的 Allow ACE | |
| `FILE_DELETE_CHILD` 的世界拒绝、fail-closed | |

即：子进程保持 Medium，但仍写不到工作区与私有 temp 之外。回滚：删掉那一行或设 `0`。

### 14.7 现状与建议

- 日常开发（`cmake`、`*.ps1`）**按「完全权限」跑**；不改插件、不再试手工改系统权限；
- 若将来 DSH 升级、或上游修复了 #423 / #5477，先复查本节，再决定是否切换回 `workspace-write`；
- 根治仍要等上游，建议一起上报这三点：
  1. `mergeAndApply()` 的 `SecurityInfo` 缺少 `0x100`（`SE_DACL_AUTO_INHERIT_REQ`），可继承 DACL 不会补到既有子对象；
  2. `grantWrite()` 对"精确命中"直接 return，使漏传播无法自愈；
  3. **Low 完整性标签也只加在根上**，而子进程被 `restrictTokenIntegrity` 降为 Low —— 既有子目录因此天然不可写。
- 相关的上游讨论：[#423](https://github.com/deepseek-ai/deepseek-harness/discussions/423)（子目录永不补授）、[#5477](https://github.com/deepseek-ai/deepseek-harness/discussions/5477)（临时目录被回收后永久失效）。
