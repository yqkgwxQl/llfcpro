## 1. 这次到底在解决什么

### 起因

`server/ChatServer1` 与 `server/ChatServer2` 是两份几乎相同的副本：

| 对比项 | 结果 |
|---|---|
| 源文件 | 40 个，其中 36 个字节级相同 |
| 真正差异 | `CMakeLists.txt` 的 target 名、`message.proto` 的一段注释、`MysqlPool.cc` 的 4 行调试注释、`config.ini` |
| 节点身份来源 | 全部来自配置（`[SelfServer] Name/Port/RPCPort`），代码里没有硬编码 |

结论：**删除一份副本、改成「一个 exe + 每个节点一份配置」几乎零信息损失。**

### 目标演进（有意为之，但要写下来）

| 阶段 | 目标 | 是否本次范围 |
|---|---|---|
| A | 消除节点副本：单 exe + `nodes/*/config.ini` | ✅ 是 |
| B | 启动可靠性：配置/端口校验、快速失败、明确退出码 | ✅ 是 |
| C | 数据层正确性：连接池超时、坏连接处理、事务状态恢复 | 🟨 附带（由 B 引出） |
| D | 横向复制到其它服务、抽公共库 | ⬜ 下一步 |

> 教训：A 做完后目标实际上从「结构」切到了「可靠性」，但当时没有明确记录，
> 导致后面越改越像「不知道自己在修什么」。

> **BL-22 的实现要点（已落地，完整记录见 §11.4）**
>
> 1. **标记时机必须由接收方决定**——`Send()` 返回只代表"入队"，连本机协议栈都还没碰到。
> 2. **用 `unique_ids` 数组而不是 `id` 水位**：水位依赖"升序连续 + 整页成功"两个隐含前提，一旦分页加了过滤条件或客户端部分落库失败就会误标。
> 3. **ACK 的判据是"这条在本地库里"**，不是"内存里有"：所以需要 `_exist_in_localcache` 这个标记；重复遇到时先补写一次，补写成功才 ACK。
> 4. **ACK 可以安全重发**，因为客户端按 `unique_id` 去重、服务端 SQL 带 `AND delivered = 0`，天然幂等。

## 7. 过程教训（流程）

1. **目标切换要写下来**：从「去重复」切到「可靠性」时，应在文档里换一行标题。
2. **可选优化必须标记并延后**：`DiscardConnection` 是增强而非修复，却引出了十个新问题。
3. **评审要有边界**：每轮只处理「崩溃 / 数据错误 / 阻塞主目标」三类，其余记 backlog。
4. **缺陷分三类对待**：新引入的回归（必须立刻修）、历史债务（排期）、设计改进（评估）。
5. **完成定义**：每个修复都配一条可执行的验收命令，没有验收就不算完成。
6. **让编译器兜底**：`-Werror=return-type` 把「靠人看」变成「编译不过」。
7. **记录优先**：本次 40+ 轮里没有一份过程记录，这是最大的流程问题——本文件就是补课。

|---|---|
| 15:33:20 | StatusServer 正常连上 Redis，5 条 `认证成功` |
| 15:34:20 → 15:34:43 | 检查线程首次运行，23 秒内新建 **9995** 条连接（5 + 9995 = 10000 = Redis 默认 `maxclients`） |
| 15:34:43 起 | 之后每条 `AUTH` 都被 Redis 以「max number of clients reached」拒绝，日志刷屏到 17:14 |
| 17:13:36 / 17:14:15 | chatserver2 / chatserver1 重启时抢不到 Redis / MySQL 连接，`空闲连接=0` → 3 秒超时 → 「节点启动中止」 |

根因是旧 `RedisConPool` 的构造函数初始化列表漏了 `fail_count_(0)`，`std::atomic<int>` 未初始化 = 垃圾值；`CheckRedisConnectValid()` 里 `while (fail_count_ > 0) { Reconnect(); fail_count_--; }` 于是把垃圾值当成了「要补的条数」，一轮补了 9995 条，且失败时计数不清零，之后每分钟都重演。

> 教训：**「循环次数来自一个没有初始化的成员」比「没有超时」更危险**——它不会卡死，而是悄悄把对端打爆。旧池子缺的不是参数，是三样东西：**计数初始化、容量上限、连接超时**。

## 10. 客户端消息状态机（2026-11-17，进行中）

### 10.1 状态定义（`client/llfcchat/global.h`）

| 值 | 含义 | 谁会设 |
|---|---|---|
| `SENDING = 0` | 已发出，等服务器回执 | 发送方（`ChatPage::on_send_btn_clicked`） |
| `FAILED = 1` | 发送失败 / 未确认 | 收到 1018 `error != 0`；或连接断开 |
| `DELIVERED = 2` | 服务器已接收（`online=true` 表示已转发给在线对端） | 收到 1018 回执 |
| `READ = 3` | 对端已读（**协议未实现**，`read.png` 已备） | 将来由已读回执设置，见 BL-20 |
| `RECEIVED = 4` | 接收方本地已收到 | 收到 1019 推送（`tcpmgr.cpp`） |

> 状态只画在**自己发的**消息上（`ChatItemBase` 的 `Self` 分支）；对方消息用 `RECEIVED`，不画图标。

### 10.2 状态存在哪：数据层，不是 UI

- 真相在 `ChatDataBase::_status`（`ChatSessionData::UpdateMsgStatus` 按 `unique_id` 改）；
- 回执到达时**同时**更新数据层和“当前还活着的气泡”；
- 切会话后重放消息时，从数据层读状态 → 不会退化成“一直发送中”。

### 10.3 为什么删掉 `Batch`（历史决策，避免再走回头路）

1. **分组是“发送侧”概念，状态更新是“接收侧”事件**：回执里本来就带全部 `unique_ids`，按 id 逐个处理即可，不需要“猜这批属于哪一批”；整批向量全等匹配（`IsMatch`）会把正确性绑死在服务端的回执粒度上。
2. **`Batch` 里混了三种生命周期不同的东西**：消息状态（活到回执/超时）、发送分组（一次请求）、UI 控件指针（只活到切会话）。混在一起必然互相踩：`shared_ptr` → double free；裸指针 → 切会话后悬空；`QPointer` → 数据层依赖 UI 层。
3. **状态要放在能重放的地方**：`Batch` 被 ack 清掉后状态就丢了；放在 `ChatDataBase` 里，切会话、重放都正确。

现行结构：`ChatDataBase._status`（数据层） + `ChatPage::_unrsp_items`（`QMap<QString, ChatItemBase*>`，只服务当前可见会话，切会话清空） + 1018 回执按 `unique_id` 逐条更新。

## 11. 消息持久化、离线投递与本地缓存（2026-11-20 ~ 11-21）

### 11.1 全链路

```
A ──1017 {to_uid, text_array[{unique_id, content, chat_time}]}──▶ ChatServer
                                                                   │
                                              ① 好友校验（GetRelation==1）
                                              ② 先落库：INSERT IGNORE message(delivered=0)
                                              │
                        ┌─────────────────────┴─────────────────────┐
                   B 在线                                     B 离线
                   │                                          │
        1019 推送 notify（含 text_array）              什么都不做（delivered 保持 0）
                   │                                          │
     B: AppendMsg（内存 + SQLite）                             │
        → 只有真的写进库，才回 1020 {other_uid, unique_ids}      │
                   │                                           │
        服务端 ConfirmChatTextMsg                              │
        UPDATE ... SET delivered=1                            │
        WHERE unique_id IN (...) AND to_uid=我 AND from_uid=他 │
        AND delivered=0                                       │
                                                              │
                                          B 下次登录/进会话 ───┘
                                          1044 {other_uid, after_id}
                                          → 1045 {chat_msg_list, max_id, has_more}
                                          → B 逐条 AppendMsg → 回 1046 → 标 delivered=1

A 的界面状态：SENDING（发出）→ DELIVERED（收到 1018，服务器收下了）
             ——注意 DELIVERED 只代表"服务器收到"，不代表"对方收到"（那需要 BL-20 的送达回执）
```

### 11.2 表结构（`server/sql/schema.sql` 的 `message`）

| 列 | 作用 | 设计理由 |
|---|---|---|
| `id` | 自增主键，**唯一排序与分页游标** | `chat_time` 来自客户端时钟，不可信；`AUTO_INCREMENT` 单调递增，天然是"水位" |
| `unique_id` | 客户端生成的 UUID，**唯一索引** | `INSERT IGNORE` 靠它实现幂等；重发/重复拉取不会多出一行 |
| `delivered` | 0=待投递 / 1=已投递 | 只有**接收方 ACK** 才会置 1（BL-22） |
| `thread_id` | 恒 0，占位 | 将来群聊/会话实体化时不用改表 |
| `chat_time` | `varchar(32)` 原样存客户端字符串 | 用 `datetime` 会被 MySQL 按会话时区解释，跨时区读出来就变了 |
| `created_at` | 服务端落库时刻 | 排障/统计；**排序不用它**（精度只到秒） |

索引：`uk_unique_id(unique_id)`、`idx_inbox(to_uid, delivered, id)`、`idx_pair(from_uid, to_uid, id)`。

### 11.3 离线拉取：正向游标（`id ASC` + `after_id`）

```sql
SELECT ... FROM message
 WHERE from_uid = ? AND to_uid = ? AND delivered = 0
   AND id > ?                       -- after_id，0 表示从头
 ORDER BY id ASC
 LIMIT ?
```

**为什么和好友/申请列表相反（那边是 `DESC` + `before_id`）**：

- 会话列表是"新的在上"，所以倒序 + 向前翻；
- **聊天记录是"老的在上、新的在下"**，而客户端 `AppendMsg` 是**尾部追加**，所以必须正序；
- 早期的 `DESC` + 正向游标是矛盾的：第 2 页会把第 1 页再拉一遍，更老的消息永远拉不到。

### 11.4 可靠确认（BL-22 的核心）

**问题**：`CSession::Send` 只是把包塞进 `_send_que`（异步），包体 > `MAX_LENGTH` 还会**静默丢弃**。原来服务端"发完就 `MarkMessagesDelivered`"，于是存在「库里标成已投递、客户端从未收到」的窗口 → 消息永久丢失。

**解法：谁收到，谁确认。**

| 消息 | 方向 | 含义 |
|---|---|---|
| `1018` | 服务端 → 发送方 | 服务器**收下了**（已落库） |
| `1019` | 服务端 → 接收方 | 有新消息 |
| `1020` → `1021` | 接收方 → 服务端 | 「我**确实收到并保存了**这些（在线推送的）」 |
| `1044` / `1045` | 客户端 ↔ 服务端 | 拉离线消息（分页） |
| `1046` → `1047` | 接收方 → 服务端 | 「我**确实收到并保存了**这些（离线拉取的）」 |

**ACK 的判据只有一条**：

> 这条消息**真的写进了本地 SQLite**，才 ACK。

客户端因此需要区分三种"新增"、两种"已存在"：

```cpp
enum class AppendMsgCode {
    ADDED,                        // 新增 + 已在库        → ACK ✅ 显示 ✅
    ADDED_MEMORY_ONLY,            // 新增 + 只在内存      → 不 ACK  显示 ✅
    ALREADY_EXISTS,               // 已存在 + 已在库      → ACK ✅
    ALREADY_EXISTS_MEMORY_ONLY,   // 已存在 + 只在内存    → 不 ACK（先尝试补写）
    PERSIST_FAILED,               // 参数非法，不入内存    → 不 ACK  不显示
};
```

判据来自 `ChatDataBase::_exist_in_localcache`（只有 `SaveMsg` 成功、或从库里回读时才为 true）。

服务端标记 SQL（`MysqlDao::MarkMessagesDelivered`）：

```sql
UPDATE message SET delivered = 1
 WHERE unique_id = ? AND from_uid = ? AND to_uid = ? AND delivered = 0
```

- `to_uid` 取自 **session**（不是报文）→ 只能标记"发给自己的"，防越权；
- `delivered = 0` → 天然幂等，重复 ACK 无副作用；
- 用逐条 `PreparedStatement` 复用（prepare 一次、execute N 次），便于逐条观察未命中的 id。

### 11.5 客户端降级模式（本地库不可用）

| `SaveResult` | 含义 | 处理 |
|---|---|---|
| `OK` | 已写入 | `_exist_in_localcache = true` → 可 ACK |
| `NOT_OPEN` | 库没打开（本次运行不可恢复） | 入内存、**不 ACK**，UI 提示一次 |
| `WRITE_FAILED` | 库开着但这次写失败 | 同上（入内存、不 ACK），下次重发时**顺便补写** |

**取舍**：可用性优先——库不可用时仍然能聊天，只是记录不持久；因为不 ACK，服务端会一直保留，库恢复后能补回来。

**代价（缺口）**：发送方本地落库失败时，自己发的消息会永久缺失（服务端历史只拉 `to_uid=我`）→ 见 BL-25 的双向历史接口。

### 11.6 本地缓存（SQLite）

- 位置：`<exe目录>/data/chatcache_<self_uid>.db`（不可写时回退到 `AppLocalDataLocation`），**按 uid 分库**，多账号隔离；
- `PRAGMA journal_mode=WAL` + `synchronous=NORMAL` + `busy_timeout=3000`；
- 表：`msg(seq INTEGER PRIMARY KEY AUTOINCREMENT, unique_id TEXT UNIQUE, other_uid, send_uid, msg_type, content, status, chat_time)`；
  - `seq` 是**本地游标**（`rowid` 在 VACUUM 后可能重排，所以显式建）；
  - `other_uid` 必须单独存：会话 key 不能从 `send_uid` 推出来（自己发的消息 `send_uid` 是自己）；
- **唯一写入口**：`ChatSessionData::AppendMsg`（发送 / 1019 / 1045 / 回读都走它）；状态由 `UpdateMsgStatus` 同步写库；
- 登录时 `Open(uid)` → `LoadSession()`，**必须在 `emit sig_switch_chatdlg()` 之前**，否则界面是空的；
- 回读时 `SENDING → FAILED`（上次进程没等到 1018，不能让气泡永远转圈）；回读用 `persist=false` 并直接标记 `_exist_in_localcache = true`。

### 11.7 本轮踩过的坑（都值得记住）

| 坑 | 现象 | 根因 |
|---|---|---|
| 1044 被绑到 `DealChatTextMsg` | 日志里"凭空多出一个 chattextmsg 请求"，还回了 1018 | `_callBacks` 复制粘贴，没改成 `GetOfflineMsg` |
| `DESC` + `id >` 游标 | 第 2 页把第 1 页再拉一遍，老消息永远取不到 | 游标方向与排序方向矛盾 |
| `refreshChatView` 先 `clearItems` 后判空 | 偶发白屏 | 破坏性操作放在了可能提前 return 之前 |
| 用 `bool` 表示 5 种状态 | 重复消息永远确认不掉、每次登录重拉 | 信息被压扁，调用方只能靠猜 |
| 查重分支缺 `return` | 同一句话出现多个气泡，越拉越多 | "已存在"滑进了"新增"逻辑，`_msg_list` 被重复 push |
| 服务端自己宣布送达 | 包被丢时 `delivered=1`，消息永久丢 | 把"入队"当成"送达" |
| `toStyledString()` | 回包体积膨胀，容易撞 2048 | 美化输出（缩进/换行） |
| 身份字段取自报文 | 可看别人的好友/申请列表、可冒充发申请 | 没用 `session->GetUserId()` |

### 11.8 验收

见 §6 的冒烟清单，另加这四条专项：

1. 在线发消息 → `SELECT delivered` 应为 1；
2. 手工把某条 `delivered` 改回 0 → 接收方重进会话 → ACK 后变 1 → **再进一次不再拉**；
3. 把本地 db 设只读 → 收发正常、每条只出现**一个**气泡、`delivered` 保持 0；恢复可写并重启后能补拉、补写、补 ACK；
4. 用 A 的会话发 1046 带 B 的 `unique_id` → 日志"未命中"，B 的消息仍是 `delivered=0`（`from_uid`/`to_uid` 双约束生效）。
